
= LRA context propagation and the `LRAContextResolver` SPI

This section explains how the "current LRA" is determined on the server side, why using a `ThreadLocal` alone is unsafe, and how the RESTEasy-backed resolver prevents leaked contexts.

== The problem: `ThreadLocal` values don't transfer when execution moves to a different thread

Narayana LRA is implemented as JAX-RS request/response filters. The inbound `ServerLRAFilter` extracts the LRA from the request and stores it in a `ThreadLocal` held by `io.narayana.lra.Current`. Several places then read it back through `Current.peek()` (which is what `NarayanaLRAClient.getCurrent()`, the outbound `ClientLRARequestFilter`, and the response-header writer all use).

This works only if the request filter and the resource method run on the *same* thread. The MicroProfile LRA specification and JAX-RS make no such guarantee. In containers such as WildFly (which uses RESTEasy), the resource method (and any outgoing client call it makes) can run on a *different, pooled* thread. This causes two problems:

* the `ThreadLocal` set by the filter is *invisible* to the resource method; or
* worse, a pooled thread still carries a *previous* request's LRA, so an unrelated request incorrectly reads the wrong context.

The second case violates the MicroProfile LRA specification: an outgoing JAX-RS call would propagate the leaked LRA instead of the LRA from the current request, enlisting a downstream participant in the wrong LRA. This causes intermittent, thread-pool-dependent MicroProfile LRA TCK failures.

== The fix: read the LRA from the propagated request context

The JAX-RS runtime already provides a solution. `ServerLRAFilter` writes the LRA into the request header `LRA_HTTP_CONTEXT_HEADER` (`Long-Running-Action`), and the JAX-RS runtime copies the request context — including the request headers — to whichever thread runs the resource method. Instead of using the `ThreadLocal`, `Current.peek()` reads the LRA from the propagated request context.

To avoid coupling `io.narayana.lra.Current` (in the `lra-service-base` module) to a specific JAX-RS implementation, the read uses a small, vendor-neutral SPI:

[source,java]
----
package io.narayana.lra.spi;

import java.net.URI;

public interface LRAContextResolver {

    /**
     * @return the LRA propagated for the request currently being processed on the
     *         calling thread, or {@code null} when there is no active request context
     *         or the request carries no LRA
     */
    URI currentLRA();
}
----

`Current` loads an implementation once through the `java.util.ServiceLoader`:

* if a resolver is registered, `peek()` compares the resolver-provided LRA with the `ThreadLocal` (see <<reconciliation>>);
* if none is registered — for example a pure, standalone client with no server request context — `peek()` uses the `ThreadLocal`, which works correctly because no cross-thread dispatch happens.

[[reconciliation]]
=== How `peek()` compares the header with the `ThreadLocal`

`peek()` checks both sources to handle programmatic context changes while rejecting leaked `ThreadLocal` values:

* *A request LRA is present* (the resolver returned a value). Use the `ThreadLocal` value only when it *matches* the request LRA. This preserves programmatic nested contexts like `NarayanaLRAClient.startLRA()` called inside the resource method. When the `ThreadLocal` contains a different LRA, it is stale or foreign (the filter and resource method ran on different threads), so the propagated header is used instead.
* *No request LRA is present* (pure client, or a non-transactional method that created a context after the header was removed). Use the `ThreadLocal`, but check it against the active-LRA cache first to reject leaked contexts from previous requests.

The same logic applies to the response path: the LRA written to the response `LRA_HTTP_CONTEXT_HEADER` is the LRA from the request, never a stale value from the pooled thread.

== Using the RESTEasy resolver

For RESTEasy deployments an implementation is provided out of the box in the `narayana-lra` (JAX-RS) module — you do not have to write or register anything. It is `io.narayana.lra.filter.ResteasyLRAContextResolver`:

[source,java]
----
public class ResteasyLRAContextResolver implements LRAContextResolver {

    @Override
    public URI currentLRA() {
        HttpHeaders headers = ResteasyContext.getContextData(HttpHeaders.class);

        if (headers == null) {
            return null;
        }

        // Use getRequestHeader + getLast (from io.narayana.lra.Current) to extract
        // the last value from multi-valued headers. This matches what ServerLRAFilter
        // does when resolving the incoming LRA. Do not use getHeaderString, which
        // comma-joins multiple values into a single string.
        String last = Current.getLast(headers.getRequestHeader(LRA_HTTP_CONTEXT_HEADER));

        return last == null ? null : URI.create(last);
    }
}
----

`org.jboss.resteasy.core.ResteasyContext#getContextData(HttpHeaders.class)` returns the propagated request headers on *any* thread RESTEasy dispatches to. This works correctly even when execution moves to a different thread.

It is registered for the `ServiceLoader` on the classpath of the `narayana-lra` module:

.`META-INF/services/io.narayana.lra.spi.LRAContextResolver`
[source]
----
io.narayana.lra.filter.ResteasyLRAContextResolver
----

Because the module dependency graph is `coordinator` → `narayana-lra` → `lra-client` → `lra-service-base`, and `lra-client` does *not* depend on `narayana-lra`, this resolver is discovered at runtime for both participant applications and the coordinator, while a standalone client that only pulls in `lra-client` finds no resolver and safely uses the `ThreadLocal`.

The `narayana-lra` module declares `resteasy-core` at `provided` scope (the RESTEasy runtime is supplied by the container), so no extra runtime dependency is added to your deployment.

== Providing your own resolver for another JAX-RS runtime

If you run on a JAX-RS runtime other than RESTEasy, prevent the same `ThreadLocal` problem by supplying your own resolver:

. implement `io.narayana.lra.spi.LRAContextResolver`, returning the LRA from your runtime's propagated request context — read the `LRA_HTTP_CONTEXT_HEADER` request header and, when it is multi-valued, use the *last* value (use `io.narayana.lra.Current#getLast` to extract it), which matches nested LRA semantics where the most recently started LRA takes precedence;
. register the implementation class in `META-INF/services/io.narayana.lra.spi.LRAContextResolver` on the deployment classpath;
. return `null` whenever there is no active request context, so `Current` uses the `ThreadLocal` instead.

`Current` loads exactly one resolver via the `ServiceLoader`. A badly registered or unloadable provider is treated as "no resolver" and logged at DEBUG level, so the system uses the `ThreadLocal` fallback instead of failing.
